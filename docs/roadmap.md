## 2. ビンゴ／クイズ結果を KV で管理者へ送る

### いまの状態

| アプリ | 結果の置き場 | 管理者への共有 |
|--------|--------------|----------------|
| ビンゴ | 端末の localStorage 中心 | なし（画面を見るだけ） |
| クイズ | 端末ローカル／URL 設定 | なし |
| アンケート | すでに **KV** で同期 | Host 画面で確認可 |

ビンゴ・クイズは「個人プレイ／URL 配布」向きのため、**結果の集約がない**。次はここを足したい、というのがこのテーマです。

現行の共有の仕方（URL パック）は [design.md §5.2](./design.md) です。アンケートの KV パターンは [design.md §8](./design.md) が手本になります。

### ゴール

- ゲスト端末で出た **ビンゴ達成** や **クイズ得点** を、サーバー側（KV）に残す  
- **管理者（幹事・司会）** が後から一覧・詳細を見られる（または通知を受けられる）

### 想定ユースケース

| 誰 | 何をしたいか |
|----|----------------|
| ゲスト | 今までどおり遊ぶ（操作を増やしすぎない） |
| 管理者 | 誰がビンゴしたか、クイズの点数分布を確認する |
| 管理者 | イベント後に結果を振り返る（TTL 内） |

### 方針案（検討用）

```text
ゲスト端末
  → POST /api/...（結果送信）
  → KV に保存（ルーム or イベント単位の key）
  → 管理者画面 or Host 用 URL で一覧表示
```

| 項目 | 案 |
|------|----|
| 識別 | アンケート同様の **ルームコード**、またはイベント用の管理キー |
| KV キー例 | `bingo:{room}` / `quiz:{room}` に結果配列を保存 |
| TTL | アンケート同様 24h 程度（当日イベント用途） |
| プライバシー | 氏名は任意・端末内だけ、など方針を先に決める |
| 管理者の見方 | 専用の簡易管理ページ、または既存 Host 画面にタブ追加 |
| 「送る」の意味 | (A) KV に溜めて管理画面で見る / (B) メールや Webhook 通知。まずは **(A) を推奨** |

※ 「管理者へ送る」は、最初からメール必須にせず、**KV 保存 + 管理画面表示** から始めると実装が軽い。通知はその次。

### ビンゴで送りたいデータの例

| フィールド | 例 |
|------------|----|
| 達成時刻 | すでに表示している日時 |
| ビンゴ数 | 何ライン達成か |
| ニックネーム | 任意（入力があれば） |
| ルーム／イベント ID | 管理者が発行 |

### クイズで送りたいデータの例

| フィールド | 例 |
|------------|----|
| 得点 / 正答数 | 例: 4/5 |
| 所要時間 | 任意 |
| ニックネーム | 任意 |
| ルーム／イベント ID | 管理者が発行 |

### 完了の目安

- [ ] ゲスト操作から結果が KV に残る  
- [ ] 管理者が URL または画面で結果一覧を見られる  
- [ ] 本番とプレビューで KV を分けられる（既存の `id` / `preview_id` 方針に合わせる）  
- [ ] 要件定義・設計書（`docs/requirements.md` / `docs/design.md`）を更新する  
- [ ] 必要ならシナリオ（SC-*）と単体（UT-*）を追加する  

### 注意（先に決めること）

- 個人情報（本名など）をどこまで扱うか  
- 改ざん（クライアントから偽スコア送信）をどこまで防ぐか（署名・Host シークレットなど）  
- アンケート用 `POLL_KV` に同居するか、別名スペースにするか

## 3. 指示文を AI エージェント数人でディスカッションして揉む

プロダクト機能というより、**ことほぎ開発の進め方**としてやりたいこと。

### ゴール

- 自分の指示文（やりたいこと・変更依頼）に対して、**AI エージェントがおおむね 3 人分の視点**で議論し、曖昧さ・抜け・トレードオフを洗い出す  
- 議論のあとで「合意したやり方」を短い指示にまとめ、そこから実装・文書更新に入る  
- いきなり 1 人のエージェントが実装を始めすぎて、意図とずれる手戻りを減らす  

### 想定イメージ

```text
自分の指示（ざっくり）
  → Agent A（要件・利用者視点）
  → Agent B（実装・既存コード適合）
  → Agent C（テスト・運用・リスク）
  → 3者のディスカッション（論点・推奨・捨て案）
  → 自分の確認 or 合意サマリ
  → 実装エージェントへ短い確定指示
```

役割の分け方は仮。例:

| 役割の例 | 見るもの |
|----------|----------|
| 利用者・幹事視点 | 「会場当日に困らないか」「Host/Guest の操作は明かか」 |
| 実装視点 | 「既存の `docs/`・`app-tools`・API と矛盾しないか」 |
| 品質・出荷視点 | 「テスト・pre-push・デプロイ・KV に影響はあるか」 |

### やり方の候補（未決定）

- Cursor の **複数 Task / サブエージェント** に同じ指示を渡し、結果を突き合わせる  
- 1 チャット内で「3 役で議論してから案を1つにまとめて」と明示する  
- 定型プロンプトや `.cursor/skills` / ルールに「着手前ディスカッション」手順を書く  

### 完了の目安

- [ ] 「指示 → 3 視点ディスカッション → 短い確定指示 → 実装」の型が文書か skill に残っている  
- [ ] 実際の変更（例: 席配置 IDEA、結果 KV など）で一度通し、手戻りが減るか感触を見る  
- [ ] 必要なら Agent 向けチェックリストを [kotohogi skill](../.cursor/skills/kotohogi-cloudflare/SKILL.md) に追記する  

### 注意

- 議論そのものが目的化しない（時間上限・「論点は最大 N 個」など）  
- 最終判断は自分（プロダクトオーナー）が持つ  
- ことほぎ本体の機能要件ではないので、仕様書（requirements / design）には載せない

## 着手順の提案

```text
1. 自動テストの強化（UT-API・Branch protection・preview KV）
2. （並行可）指示文の複数 AI ディスカッション型を試す・型にする（§3）
3. 結果送信 API + KV 保存（ビンゴ or クイズのどちらか一方から）
4. 管理者向け一覧 UI
5. （任意）通知・改ざん対策の強化
```

テスト基盤があると、結果送信 API を足したときの退行も防ぎやすい。  
大きな機能に入る前に §3 の型があると、指示の食い違いを先に潰しやすい。
