## 1. 用語集（この文書で使う言葉）

初めて読む方向けに、出てくる言葉を短く説明します。すでに知っている項目は飛ばして構いません。

| 用語 | 読み・別名 | 意味（このプロジェクトでの使い方） |
|------|------------|--------------------------------------|
| **自動テスト** | — | 決めた手順をプログラムが実行し、期待どおりか判定すること |
| **単体テスト** | ユニットテスト / L1 | 小さな部品（関数など）だけを切り出して確かめる。速い。画面は開かない |
| **E2E テスト** | End-to-End / L2b | 実際のブラウザ操作に近い形で、最初から最後まで一連の流れを確かめる |
| **スモークテスト** | 煙試験 / L2 | 「火が出ていないか」程度の最低限の疎通確認。深い網羅はしない |
| **ガーキン記法** | Gherkin | 「前提・もし・ならば」のように、**日本語や英語のシナリオ文**でテスト内容を書く書き方。ファイル拡張子は `.feature` |
| **シナリオ** | — | 「Host が入室し、Guest が投票できる」のような、1本の確認ストーリー |
| **ステップ** | — | シナリオを構成する1行（「もし LPを開く」など）。裏でプログラムが動く |
| **CI** | Continuous Integration（継続的インテグレーション） | コードを GitHub に送るたびに、クラウド上でビルドやテストを自動実行する仕組み |
| **CD** | Continuous Delivery / Deploy | テスト成功などを条件に、公開（デプロイ）までつなげる流れ |
| **GitHub Actions** | — | GitHub 上で CI/CD を動かす無料枠のある仕組み。設定ファイルは `.github/workflows/` |
| **Workflow / Job** | ワークフロー / ジョブ | Workflow＝一連の自動処理の定義。Job＝その中の作業単位（例: `unit` と `e2e`） |
| **Artifact** | 成果物 | CI が残したファイル（ここでは **テストの録画動画** など）。後からダウンロードできる |
| **husky** | ハスキー | `git push` などの直前に、決めたコマンドを自動で走らせる道具（Git フック） |
| **pre-push** | — | 「リモートへ送る直前」に走るフック。ここでは単体テストを強制 |
| **コミット / プッシュ** | commit / push | コミット＝自分の履歴に記録。プッシュ＝その履歴を GitHub などへ送る |
| **PR** | Pull Request | 変更を `main` などに取り込んでもらうための提案・レビュー用のページ |
| **ブランチ** | branch | 作業用の枝。`main`＝本番向け本流、`preview`＝試し用、など |
| **本番 / 非本番** | production / preview | 本番＝会場が使う公開環境。非本番＝壊しても会場に影響しにくい確認用環境 |
| **デプロイ** | deploy | 作ったアプリをインターネット上のサーバー（ここでは Cloudflare）に載せて公開すること |
| **KV** | Key-Value ストア | Cloudflare の簡易データベース。アンケートの票など「みんなで共有するデータ」を置く |
| **`POLL_KV`** | — | このアプリがアンケート用に使う KV の接続名（バインディング名） |
| **モック / メモリ** | mock | 本物の KV の代わりに、テスト用の偽物やパソコン内の一時保存を使うこと |
| **API** | — | 画面の裏でデータをやり取りする入口。例: `/api/poll/ルームコード` |
| **HTTP / GET / POST** | — | Web の通信の仕方。GET＝取得、POST＝作成・更新・投票など |
| **LP** | ランディングページ | ことほぎの紹介トップページ |
| **Host / Guest** | 司会 / ゲスト | アンケートで、進行する人（Host）と投票する人（Guest） |
| **退行** | レグレッション | 以前できていたことが、新しい変更で壊れること |
| **合否 / PASS / FAIL** | — | テストが成功したか失敗したか |
| **OSS** | Open Source Software | 無料で使えるオープンソースのソフト。Vitest や Playwright など |
| **webm** | — | ブラウザで再生できる動画ファイル形式。E2E の録画に使う |

## 2. 目的

**壊れた変更を、会場が使う本番（`main` ブランチ）に載せないこと。**

特に次のような「当日困る」変化を、早く見つけたいです。

- ルームコードの扱いがおかしくなる
- アンケートの投票や同期が壊れる
- 紹介ページや余興画面の最低限の操作ができなくなる

### 2.1 やらないこと（非目的）

次は、いまの自動テストの対象外です。

| やらないこと | 理由 |
|--------------|------|
| 本番の KV（`POLL_KV`）を CI から書き換えて試す | 会場データが汚れたり、不安定・課金リスクがある |
| 有料のテスト専用クラウドサービスを使う | コストを増やさない方針 |
| デザインの見た目を機械だけで完璧に保証する | 当面は人の目と非本番確認で補う |

## 3. 原則（守ること）

| ID | 内容 | かんたんな言い換え |
|----|------|--------------------|
| T-P01 | 確認の順番は **単体 → 非本番 → 本番** | 本番でいきなり試さない |
| T-P02 | 単体は **本物の KV を使わない** | パソコン内のメモリや偽物で足りる |
| T-P03 | CI・スモークは **本番 KV を更新しない** | 会場用データを触らない |
| T-P04 | 非本番で KV を使うなら、できれば本番と分ける | 試し投票が本番に混ざらないようにする |
| T-P05 | テスト用ルームは **`T` で始める**（例: `T9A1`） | 本番イベントのコードとぶつかりにくくする |
| T-P06 | CI の結果は **GitHub 上の Linux を正**とする | 自分の PC（特に Windows ARM）だけ通っても安心しすぎない |
| T-P07 | 有料のテスト基盤は使わない | Vitest / Playwright など OSS で完結 |

## 4. テストの階層（どんな確認を積み重ねるか）

イメージは「安い・速い確認」から「本番に近い確認」へ進む階段です。

```text
L1   単体テスト          部品が正しいか（速い・毎回）
L2   スモーク            公開先に届くか（短い HTTP 確認）
L2b  E2E（動画付き）     ブラウザ操作の流れが正しいか
L3   非本番の手動確認    人がプレビューで会場どおり触る
L4   本番                会場用。上を通ってからだけ
```

| 層 | なにをするか | コマンド例 | これで分かること | これだけでは分からないこと |
|----|--------------|------------|------------------|----------------------------|
| **L1** | 関数などの小さな部品を確かめる | `npm test` | ルーム正規化や票の計算などが仕様どおりか | 実際の画面・Cloudflare 上の動き |
| **L2** | 公開 URL に短い通信を送る | `npm run smoke` | LP が開くか、投票 API が最低限動くか | ビンゴ／クイズの画面、細かい UI |
| **L2b** | ブラウザを自動操作する | `npm run test:e2e` | シナリオどおり操作できるか。**録画で後から見られる** | 全機種・全ブラウザ、本番 KV |
| **L3** | 人がプレビューを触る | （手順書） | 会場オペに近いか | 毎回の網羅的な自動チェック |
| **L4** | 本番公開後の最終確認 | （デプロイ後） | 公開環境で使えるか | 試し打ちの場所としては使わない |

「いつコマンドを打つか／push で何が強制されるか」は [ops/testing.md](./ops/testing.md) を見てください。

## 6. L1 単体テスト（いま実装済みの内容）

### 6.1 対象

| 対象 | ファイル | 何を見ているか |
|------|----------|----------------|
| ルームコード・票の整え方 | `src/lib/poll.ts` | API が使う「きれいにする」処理 |

コードを変えるときは、できれば **この節の期待結果も一緒に直す**（仕様と実装がずれないように）。

### 6.2 ルームコード `normalizeRoom`

「英語・数字以外を捨てて、大文字にして、最大4文字にする」処理です。

| ID | 入力例 | 期待する結果 | 補足 |
|----|--------|--------------|------|
| UT-ROOM-01 | `"ab-12"` | `"AB12"` | 記号を除き大文字化 |
| UT-ROOM-02 | `"  xy9z  "` | `"XY9Z"` | 空白も実質無視 |
| UT-ROOM-03 | `"toolongroom"` | `"TOOL"` | 長すぎる場合は先頭4文字 |
| UT-ROOM-04 | `"a1"` / `""` | `"A1"` / `""` | 短い場合はそのまま。短いものをエラーにするのは API 側 |

実装されたテスト: `src/lib/poll.test.ts`

### 6.3 票の配列 `normalizeVotes`

質問の選択肢の数と、票の配列の形を揃える処理です。おかしい値は 0 にします。

| ID | 条件 | 期待 |
|----|------|------|
| UT-VOTE-01 | 票データが無い | 全部 0 で埋めた配列になる |
| UT-VOTE-02 | ある質問の票の個数が選択肢と合わない | その質問の行はやり直し（全 0） |
| UT-VOTE-03 | 小数・マイナス・数値でないもの | 使える正の数だけ残し、あとは 0 |

実装されたテスト: `src/lib/poll.test.ts`

### 6.3b 余興共通ロジック `party-logic`（UT-PARTY-\*）

幹事・進行ツール群（TOOL-\*）が使う乱数系の純粋関数を、**種を固定して決定的に**検証する。対象は `public/app-tools/shared/party-logic.js`、テストは `src/lib/party-logic.test.ts`。

| ID | 対象 | 期待 |
|----|------|------|
| UT-PARTY-SHUFFLE-01〜03 | `shuffle` | 要素を保つ／元配列を壊さない／同じ種で再現 |
| UT-PARTY-DRAW-01〜02 | `drawOne` | 1つ選び残りが減る／空なら null |
| UT-PARTY-DRAW-03〜06 | `drawDifferent` | 直前と同じ値を選ばない／残りが減る／候補が直前だけなら返す／空なら null |
| UT-PARTY-RANK-01〜03 | `rankScores` | 高得点が1位／同点は同順位で次が飛ぶ／マイナス・空でも壊れない |
| UT-PARTY-GROUP-01〜03 | `splitIntoGroups` | 全員配分／人数差は最大1／空でも指定数の空グループ |
| UT-PARTY-SIZE-01 | `splitBySize` | 各グループが最大 size 人 |
| UT-PARTY-BINGO-01〜02 | `bingoNumbers` / `bingoLetter` | 1〜75 連番／列頭文字 B I N G O |
| UT-PARTY-BILL-01〜03 | `splitBill` | 割り切れれば同額／単位切り上げで集金は合計以上／差は unit 以内 |
| UT-PARTY-AMIDA-01〜04 | `generateLadder` / `resolveLadder` | 解は全単射／横線なしは恒等／1本は隣を入替／生成線は非隣接 |
| UT-PARTY-KING-01 | `kingGame` | 1..N を1つずつ配り王様番号は範囲内 |

これらは種を渡すため乱数に依存せず、CI でも安定して PASS する。

### 6.3c 余興共通 UI 部品 `ui`（UT-UI-\*）

TOOL-\* の操作感を支える共通部品（design §5.3b）のうち、**DOM を触らない純粋関数**を検証する。対象は `public/app-tools/shared/ui.js`、テストは `src/lib/app-ui.test.ts`。

トースト・コピー・Wake Lock などブラウザ API に依存する部分はここでは扱わず、E2E（SC-TOOLS-07）で確認する。

| ID | 対象 | 期待 |
|----|------|------|
| UT-UI-ESCAPE-01〜03 | `escapeHtml` | `< > & " '` を実体参照に／普通の名前はそのまま／null は空文字 |
| UT-UI-LINES-01〜04 | `parseLines` | 空白と空行を落として件数を返す／重複名を1回だけ報告／重複なしは空／空入力でも落ちない |
| UT-UI-COUNT-01〜03 | `formatCount` | 件数と単位を並べる／0件は「未入力」と分かる／数値でない値は0扱い |
| UT-UI-FORMAT-01〜05 | `formatNumberedList` / `formatGroups` / `formatPairs` | 番号付き・チーム名と人数・矢印でつなぐ／見出しは差し替え可／空は空文字 |

`escapeHtml` は表示崩れ対策（要件 T-10）そのものなので、ここが落ちたら参加者名の表示を疑う。

## 7. L2 スモーク（いま実装済みの内容）

「公開されている URL に、短い通信だけ送って生きているか見る」確認です。ブラウザは開きません。

### 7.1 前提

| 項目 | 内容 |
|------|------|
| 環境変数 `SMOKE_BASE_URL` | 確認したいサイトの住所（末尾の `/` は付けない）。**本番の URL は使わない** |
| 未設定のとき | スクリプトはエラーで止まる（GitHub では Secret が無いときスキップ可） |
| ルームコード | 毎回 `T` で始まるランダムな4文字 |

### 7.2 シナリオ SMK-POLL-01

| 順 | やること | 成功の条件 |
|----|----------|------------|
| 1 | トップページを取得（GET） | HTTP が成功（だいたい 200 番台） |
| 2 | ルームを作成・更新（POST `upsert`） | HTTP が成功 |
| 3 | 1票入れる（POST `vote`） | 成功し、票数が 1 になっている |
| 4 | ルーム状態を取得（GET） | HTTP が成功 |

実装: `scripts/smoke.mjs`

### 7.3 L2 の合否

全部成功すること。失敗したプレビューは、本番にマージする候補にしないこと。

## 8. L2b E2E（ガーキン + 動画）（いま実装済みの内容）

### 8.1 書き方

1. **ガーキン**で「何をしたいか」を `e2e/features/*.feature` に書く（日本語可）
2. 各行に対応する操作を `e2e/steps/*.ts` に書く（Playwright がブラウザを動かす）
3. 実行すると **動画（webm）** が残るので、後から「何が起きたか」を目で追える

有料の録画サービスは使いません。

### 8.2 シナリオ一覧

詳細な合格条件は **[scenario-spec.md](./scenario-spec.md)** を正とする。

## 9. いつ・どこで走らせるか

**操作のくわしい説明・関係ファイルの場所・pre-push の意味**は [ops/testing.md](./ops/testing.md) を正とします。  
ここでは仕様としての要約だけ書きます。

| あなたがすること | どこでテストが走るか | 強制される内容 | 主な関係ファイル |
|------------------|----------------------|----------------|------------------|
| `git commit`（記録） | ローカル | **なし**（作業中の途中保存を妨げない） | — |
| `git push`（GitHub へ送る） | ローカル（husky **pre-push**） | **L1 単体**。失敗したら push 自体が止まる | `.husky/pre-push` → `npm test` |
| すべての push / PR | GitHub Actions **Test** | reusable **Quality**（`unit` + `e2e`）。動画 Artifact `e2e-videos` | `test.yml` → `quality.yml` |
| `main` / `master` への push | 加えて **Deploy to Cloudflare** | 同じ Quality を**もう一度**通してから `deploy`（失敗したら公開しない） | `deploy-cloudflare.yml` |

補足:

- **なぜ pre-push は単体だけか**: E2E は遅く、push のたびに強制すると習慣が壊れやすい。重い確認は GitHub 側で担保する（詳しくは [ops/testing.md §2](./ops/testing.md#2-なぜこう分けているか設計の意図)）
- L2 スモーク（`npm run smoke`）は Secret `SMOKE_BASE_URL` があるときだけ Quality の `unit` ジョブで任意実行（未設定ならスキップ）。実装は `scripts/smoke.mjs`
- Test は全ブランチ。Deploy は `main`/`master`（と手動 `workflow_dispatch`）だけ
- ローカル husky は `--no-verify` で回避できるため、**マージボタンまで止める**には Branch protection で Quality 由来の `unit` / `e2e` を必須にする（手順は [ops/testing.md](./ops/testing.md)）

## 12. これから足すテスト（予約）

優先度は [roadmap.md](./roadmap.md) に合わせます。実装したら、この仕様書の該当節にケースを正式追加します。

| 優先 | ID 案 | 層 | 内容 |
|------|-------|-----|------|
| 高 | UT-API-* | L1 | アンケート API の vote / 進行などをメモリでテスト |
| 高 | UT-BINGO-* | L1 | ビンゴ判定を関数にして単体テスト |
| 中 | UT-PACK-* | L1 | URL 圧縮（UrlPack）の pack/unpack |
| 中 | SMK-* | L2 | スモークに進行・結果表示を追加（Secret 運用の定着） |
| 低 | SC-* 追加 | L2b | 例: ゲスト待機、Host 票クリア、ビンゴ共有 URL |

※ SC-POLL-03（Host 投票不可）・SC-BINGO-01（ビンゴ達成）は **実装済み**（予約ではない）。

KV の扱い: 単体・API は **偽物／メモリ（方針 A）**。本物に近い確認は **プレビュー専用 KV（方針 B）**。本番 KV 直叩き（方針 D）は禁止。
