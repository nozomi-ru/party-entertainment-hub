## 0. この文書の読み方

要件定義書は、実装の細部（どのファイルか、どの API か）より先に、**プロダクトとして守る約束**を書く場所です。

| 読みたいこと | この文書のどこ / 別文書 |
|--------------|-------------------------|
| なぜ作るか | §1 目的 |

| 何がスコープか | §3 プロダクト構成 |
| 機能の一覧（ID 付き） | §4 機能要件 |

## 1. 目的

結婚式・パーティーの幹事・司会が、特別な機材なしで余興（交流ビンゴ・クイズ・リアルタイムアンケート）を実施できる Web アプリ群と、その紹介・配布用ランディングページを提供する。

「ことほぎ」という名前の LP から各余興へ案内し、会場のスマホだけで完結することを目指します。

### 1.1 解決したい課題

- 進行準備や台本づくりの負担が大きい
- ゲスト同士のアイスブレイク手段が限られる
- 会場全体の一体感を作りにくい
- 景品・ギフト選びの導線が弱い

---

## 2. 対象ユーザー

| ロール | 説明 | 主な利用 |
|--------|------|----------|
| 幹事・司会（Host） | 会場スクリーンや自端末で進行 | ルーム作成、問題編集、結果表示、共有 URL 配布 |
| ゲスト（Guest） | 手元のスマートフォン | 共有 URL から参加・回答・投票 |
| サイト訪問者 | LP 閲覧者 | アプリ体験・機能理解・アフィリエイト導線 |

Host / Guest は主にアンケートで役割が分かれます。ビンゴ・クイズは「設定を配る人」と「遊ぶ人」が同じ URL を開く形でも成立します（DB なしの URL 共有）。

## 3. プロダクト構成（スコープ）

| ID | 名称 | 種別 | 概要 | 主なパス |
|----|------|------|------|----------|
| LP | ランディングページ | Next.js | ブランド紹介・機能導線・アフィリエイト | `src/app/` |
| BINGO | 人間ビンゴ | 静的 HTML | 3×3 交流ビンゴ | `public/app-tools/wedding-bingo/` |
| QUIZ | 新郎新婦クイズ | 静的 HTML | 4択クイズ | `public/app-tools/wedding-quiz/` |
| POLL | リアルタイムアンケート | 静的 HTML + API | Host/Guest 同期投票 | `public/app-tools/wedding-poll/` + `/api/poll` |

対象外（将来候補。詳細は [roadmap.md](./roadmap.md)）:

- ユーザー認証・アカウント管理
- 永続的なイベント履歴の管理画面
- ネイティブアプリ
- ビンゴ／クイズ結果のサーバー集約（優先テーマ2として検討中）

## 4. 機能要件

### 4.1 ランディングページ（LP）

| ID | 要件 | 優先度 |
|----|------|--------|
| LP-01 | ブランド名・タグライン・説明をヒーローで提示する | 必須 |
| LP-02 | 課題→解決のセクションを表示する | 必須 |
| LP-03 | 各アプリ（ビンゴ／クイズ／アンケート）への導線を持つ | 必須 |
| LP-04 | アフィリエイト／おすすめリンクを設定ファイルから差し替え可能にする | 必須 |
| LP-05 | CTA・機能リンクを `src/config/site.ts` で一元管理する | 必須 |

**補足:** 文言や URL をコード中に散らさず、`site.ts` を単一の差し替え口にします。デザイン方針の詳細は Cursor skill と LP コンポーネント側の実装を参照。

### 4.2 人間ビンゴ（BINGO）

| ID | 要件 | 優先度 |
|----|------|--------|
| B-01 | 3×3 マスを表示する（中央は FREE「主役の2人」） | 必須 |
| B-02 | マスをタップしてゲスト名を入力・表示できる | 必須 |
| B-03 | 縦・横・斜めのビンゴ判定をし、達成数を表示する | 必須 |
| B-04 | 初回ビンゴ達成時に日時（日付・時分秒）を表示する | 必須 |
| B-05 | マス文言を編集できる | 必須 |
| B-06 | マス設定を URL（`?c=`）に圧縮して共有できる（名前は共有しない） | 必須 |
| B-07 | 端末内にラベル・入力名を保存し、再訪時に復元できる | 必須 |
| B-08 | リセットで設定・名前を初期化できる | 必須 |

**補足:** 名前は端末の localStorage のみ。共有 URL にはラベル（マス文言）だけを載せ、プライバシーを守ります。

### 4.3 新郎新婦クイズ（QUIZ）

| ID | 要件 | 優先度 |
|----|------|--------|
| Q-01 | 複数問・4択のクイズを実施できる | 必須 |
| Q-02 | 回答直後に正誤フィードバックを返す | 必須 |
| Q-03 | 最終スコアとレビューを表示する | 必須 |
| Q-04 | 問題・正解を編集・追加・削除できる（最低1問） | 必須 |
| Q-05 | 問題セットを URL（`?c=`）に圧縮して共有できる | 必須 |
| Q-06 | 端末内に問題を保存し、再訪時に復元できる | 必須 |

**補足:** ビンゴと同様、DB なしで `?c=` により別端末へ同じ問題セットを配れます。

### 4.4 リアルタイムアンケート（POLL）

| ID | 要件 | 優先度 |
|----|------|--------|
| P-01 | 英数字4文字のルームコードでセッションを識別する | 必須 |
| P-02 | Host はルームを作成・進行（前後質問・結果表示・票クリア）できる | 必須 |
| P-03 | Host は投票できない（選択肢は表示のみ） | 必須 |
| P-04 | Guest は選択肢を選んで1問につき1票投票できる | 必須 |
| P-05 | ゲスト用 URL（`?room=XXXX`）を開くと Guest として自動入室し、すぐ投票できる | 必須 |
| P-06 | Host 画面にゲスト用 URL の表示・コピーができる | 必須 |
| P-07 | Host が未作成の場合、Guest は準備完了まで待機できる | 必須 |
| P-08 | 投票・進行状態を参加者間でほぼリアルタイムに同期する | 必須 |
| P-09 | 結果は Host が公開したときのみ全員に表示する | 必須 |
| P-10 | Host は質問内容を編集し、ルームに反映できる | 必須 |
| P-11 | セッションデータは一定時間後に自動削除される（24時間想定） | 必須 |

**補足（オペレーション上の重要点）:**

- Host は「進行役」で、票を入れない（P-03）。誤操作で結果が歪まないようにする
- Guest は URL を開いたらすぐ投票できること（P-05）が当日の体験の核
- `mode=host` だけでは自動入室しない（ボタン操作が必要）。設計書 §8.3 参照
- 同期は約 **2秒** 間隔のポーリング（N-02）。WebSocket は使わない

### 4.5 共通

| ID | 要件 | 優先度 |
|----|------|--------|
| C-01 | スマートフォン中心の操作に耐える UI とする | 必須 |
| C-02 | ビンゴ／クイズは DB なしで URL 共有により完結する | 必須 |
| C-03 | アンケートのみサーバー側同期（本番は Cloudflare KV）を用いる | 必須 |

## 5. 非機能要件

| ID | 分類 | 要件 |
|----|------|------|
| N-01 | 可用性 | Cloudflare Workers 上で公開し、当日の短時間利用に耐える |
| N-02 | 性能 | アンケート同期は約2秒間隔のポーリングで実用的に追従する |
| N-03 | スケール | 結婚式・パーティー規模（数十〜百数十名程度）を想定。厳密な同時投票の原子性は必須としない |
| N-04 | セキュリティ | 認証なし。ルームコード推測耐性は簡易（4文字）。機微情報は扱わない前提 |
| N-05 | プライバシー | ビンゴの氏名は端末ローカル。アンケート票はルーム単位・TTL 付き |
| N-06 | 運用 | GitHub 連携または CI により Linux 上でビルド・デプロイできる |
| N-07 | 開発 | ローカル `npm run dev` で LP・静的アプリ・アンケート（メモリ同期）を確認できる |
| N-08 | 互換 | モダンモバイルブラウザ（Safari / Chrome 系）を主対象とする |

壊れた変更を本番に載せないためのテスト方針は、要件そのものではなく [test-spec.md](./test-spec.md) と [ops/testing.md](./ops/testing.md) で定義します。

## 6. 制約・前提

- Windows ARM 環境ではローカルの `wrangler` / `workerd` による preview・deploy が失敗しうる → Cloudflare 側 Linux ビルド（GitHub Actions または CF Git 連携）を推奨。手順は [ops/preview.md](./ops/preview.md)
- 外部画像は Unsplash 等を想定し、Next.js 画像最適化はオフ（`images.unoptimized: true`）
- アフィリエイト URL は設定差し替え前提（初期値はプレースホルダ可）。差し替え口は `src/config/site.ts`
- 秘密情報（`.dev.vars` / API Token）は Git に含めない

## 7. 受け入れ条件（抜粋）

当日デモやリリース判定で「ここまでできれば合格」とするラインです。  
自動シナリオとの対応は [scenario-spec.md](./scenario-spec.md) の §1 に表があります。

1. LP から3アプリに遷移できる → 主に SC-LP-02
2. ビンゴで名前入力→ビンゴ達成→日付付き時刻が表示される → SC-BINGO-01
3. クイズを URL 共有し、別端末で同じ問題セットが開く → SC-QUIZ-01
4. Host が入室→ゲスト URL を開く→Guest が投票→Host が結果表示できる → SC-POLL-01 / SC-POLL-02
5. Host が選択肢をタップしても票が増えない → SC-POLL-03
6. Cloudflare へデプロイ後、本番 URL で上記が再現できる → 主に手動 L3（本番）。手順は [ops/preview.md](./ops/preview.md) のあと本番確認
